**Status**: D07 포함 구현·자동47건·실제 브라우저5단계 확인 완료. 관리자 최종 현장 사용성 승인은 대기. [최신 QA](../../deliverables/D07_QA_REPORT.md).

**최신 기술 검증(2026-10-27)**: [정적/예외 보강](../../deliverables/HARDENING_REPORT.md), 정적19파일 오류0/경고0 및65개 테스트 통과. D07 업무 기준과 세 시점 요약은 유지했다. 현장 최종 사용성 승인과 구분한다.

## Overview

로컬 브라우저에서 제공 기록을 비교해 다음 교대의 우선 알람, 이어받을 생산/현장 업무, 상태/데이터 확인 항목을 구분한다. 인계 사유와 원본 근거를 확인하고 짧은 요약을 복사한다. 다음 근무자가 첫 5분 안에 무엇을 확인할지 파악하는 것이 목표다.

이 문서는 기능·업무 규칙의 대표 명세다. requirements/의 상세 명세가 아래 FR을 정밀화하며 acceptance.md가 검증 연결을 제공한다. 세부 기술 스택·코드·실행 명령은 plan.md에 기록한다.

## Clarifications

### Session 2026-10-26

- Q: 복사 요약의 분량과 정렬은? → A: D07 관리자 승인. 간결 요약을 기본으로 영역별 최대 5건(총 최대 15건), 잔여 건수 안내. 전체 상세를 별도로 조회·복사한다. 보류→진행→메모 LOT→기타 현장 요청 순, 같은 순위는 최신 확인 가능 시각이 이른 순. 데이터 확인은 승인된 5유형 순 및 같은 유형 최신 가용 순. 상세 조건은 requirements/06-summary-and-display-order.md.

- Q: 오래된 요청만으로 완료 LOT를 신규 인계할 것인가? → A: 최근 24시간을 기준으로 사용. 더 오래된 메모는 이미 인계 대상인 항목의 관련 근거로 유지.
- Q: 메모/LOT 설비가 다른 명확 요청으로 LOT를 편입할 것인가? → A: 메모는 표시하되 관계 확인 전 해당 메모만으로 LOT를 편입하지 않음.
- Q: 메모 12종의 분류는 무엇인가? → A: 관리자가 추가 11종을 승인했고 기존 확인 대기 1종과 합쳐 총 12종을 확정함(D03). 후속 확인·지속 관찰·참고 정보·분류 확인 필요를 구분하며, 모든 메모의 조치 완료는 미확정이다.
- Q: CSV/열 누락 또는 일부 행 파싱 실패 때 어떻게 할 것인가? → A: 읽을 수 있는 부분만 제공하고 불완전 결과임을 명시.
- Q: 정확히 24시간 전 기록을 최근 범위에 포함하는가? → A: 제외. 최근 범위는 `(T-24시간, T]`.
- Q: 취소 LOT의 hold 미확인과 승인된 후속 업무가 동시에 있으면 후속 상태를 어떻게 표현하는가? → A: 관리자가 메모 기반 인계 확정과 보류 수량 미확인을 독립 표시하도록 승인함(D06). 보류 관련 후속 확인 필요성·조치 완료는 미확정이고 메모만으로 긴급 확정하지 않는다. 보류 0만으로 유효한 메모 인계를 제거하지 않는다.
- 재검토 보완: 관리자 기존 예시 `정비 결과 확인 요청`은 후속 확인으로 승인된 근거가 있어 미등록 문구로 취급하지 않는다. 실제 입력의 `정비 결과 기록 확인`은 계속 분류 확인 필요다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 우선 확인할 미해결 알람 파악 (Priority: P1)

교대 책임자로서 선택한 교대에 확인할 수 있었던 중요한 미해결 알람과 그 이유를 먼저 보고 싶다.
**Why this priority**: 해결 문제의 재표시, 중복 오인, 미래 정보 반영을 막는 핵심 가치다.
**Independent Test**: 설비/사전/알람만으로 현재·과거 교대의 알람 목록과 각 근거를 확인한다. 빠진 자료는 불완전으로 명시한다.
**Acceptance Scenarios**:
1. **Given** HIGH와 오래된 LOW가 미해결, **When** 교대 조회, **Then** HIGH를 먼저 표시하고 동일 심각도는 긴 지속시간순이다.
2. **Given** 해제가 교대 후 수신, **When** 과거 교대 조회, **Then** 해제를 과거 상태와 상세 근거에 사용하지 않는다.
3. **Given** 중복 발생·HEARTBEAT·고아 해제, **When** 조회, **Then** 중복과 HEARTBEAT는 발생 건수를 늘리지 않고 고아 해제는 상태 확인 목록에 있다.

### User Story 2 - 이어받을 생산·현장 업무 파악 (Priority: P1)

교대자로서 진행·보류·후속 확인·지속 관찰을 이어갈 LOT와 현장 업무를 확인하고 싶다.
**Why this priority**: 생산 완료와 후속 업무 완료를 구분해 인계 누락을 줄인다.
**Independent Test**: LOT/메모의 가용 버전과 확정 요청 사례를 사용해 진행·보류·후속 인계와 관계 불일치를 대조한다.
**Acceptance Scenarios**:
1. **Given** 완료 LOT에 보류 양수, **When** 조회, **Then** 완료와 무관하게 보류 인계에 포함한다.
2. **Given** 취소 LOT에 hold 공란, **When** 조회, **Then** 0이나 긴급으로 바꾸지 않고 데이터 확인 상태를 표시한다.
3. **Given** 최근 명확 요청과 완료 LOT의 설비가 다름, **When** 조회, **Then** 메모·관계 확인은 표시하되 메모만으로 LOT를 편입하지 않는다.
4. **Given** 진행/보류 LOT에 오래된 메모, **When** 근거 조회, **Then** 원문을 볼 수 있고 오래됐다는 이유로 완료 처리하지 않는다.

### User Story 3 - 데이터 문제와 실제 업무 구분 (Priority: P1)

책임자로서 인계 업무와 데이터 확인이 필요한 항목을 구분하고 원본을 비교하고 싶다.
**Why this priority**: 오류를 생산 위험으로 오인하거나 정상 업무를 숨기는 일을 막는다.
**Independent Test**: LOT-XBAD, 불일치 메모, 동일 버전 충돌 자료를 각각 표시해 사유와 원본 보존을 확인한다.
**Acceptance Scenarios**:
1. **Given** 최신 수량 오류, **When** 조회, **Then** 원본 오류 revision을 보여주고 과거 버전으로 정상화하지 않는다.
2. **Given** 진행 업무에 수량 오류도 있음, **When** 조회, **Then** 업무 사유와 품질 문제를 모두 확인하고 같은 LOT임을 알 수 있다.
3. **Given** 일부 입력을 읽을 수 없음, **When** 조회, **Then** 읽을 수 있는 부분의 결과와 불완전 상태·누락 범위를 표시한다.

### User Story 4 - 교대 요약 검토와 복사 (Priority: P2)

교대자로서 같은 시점의 알람·업무·데이터 확인을 짧은 인수인계 요약으로 가져가고 싶다.
**Why this priority**: 판정 결과를 기존 인수인계 업무에 전달할 수 있게 한다. P2는 구현 순서이며 MVP 제외가 아니다.
**Independent Test**: 생성된 판정 자료로 요약과 상세를 대조하고 복사 성공/실패를 확인한다.
**Acceptance Scenarios**:
1. **Given** 선택 교대 결과, **When** 요약 복사, **Then** T·인계 사유·근거 ID·이력 한계와 불완전 여부가 함께 복사된다.
2. **Given** 복사 실패, **When** 사용자가 확인, **Then** 실패 안내와 가져갈 수 있는 요약 원문이 있다.

### Edge Cases

지연 수신, 이전 교대보다 오래된 미해결, 고아 해제, 전환 시각 동일, 사건/버전 충돌, 상태 ID 누락, HEARTBEAT 공란, 수량 NULL/0, 최신 수량 오류, 미확정 합계, 미래 LOT 상세, 메모 설비 불일치, 오래된/모호한 메모, 부분 입력, 24시간 하한 제외, 기록 없는 시점과 데이터 끝 이후 조회를 처리한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-036**: 간결 요약을 기본 표시/복사하고 전체 상세 요약을 별도로 조회/복사해야 한다. 간결 요약은 알람·생산/현장 업무·데이터 확인 영역별 최대 5건, 총 최대 15건이며 생략 건수와 전체 상세 안내를 제공해야 한다.
- **FR-037**: 간결 요약의 표시 항목마다 대상 ID·상태·사유·다음 조 확인 사항·원본 식별자를 포함해야 한다. 제공 기록/기준 시각/불완전/이력 한계도 보존하고, 생략 대상 ID 전부를 나열하지 않는다.
- **FR-038**: 생산/현장 통합 인계 순서는 보류 양수 LOT→IN_PROGRESS LOT→승인 메모 기반 LOT→기타 최근 후속 확인/지속 관찰 현장 업무다. 한 LOT는 최고 우선 조건으로 한 번만 표시하며 모든 사유는 상세에 유지한다. 같은 순위는 최신 확인 가능 시각이 이른 순이다.
- **FR-039**: 데이터 확인은 알람 상태 기록 충돌→LOT 수량 모순/최신 revision 충돌→필수 수량/상태 누락→연결 불일치→기타 순으로 표시한다. 같은 유형은 최신 확인 가능 시각이 최근인 순이다.
- **FR-040**: 표시 순서를 위험 등급으로 해석하지 않아야 한다. LOT의 동일 설비 미해결 HIGH 사건 연결을 보여주되 실제 피해/인과관계를 확정하지 않는다.
- **FR-041**: 전체 상세는 간결 요약에서 빠진 모든 인계/확인 항목과 관련 메모를 보존하며, 원본 파일명·식별자·판정 사유를 조회·복사할 수 있어야 한다.
- **FR-042**: 실제 브라우저에서 관리자 지정 5단계(초기 HIGH, 보류/진행/현장 요청 구분, 원본 조회, 간결 복사, 데이터 확인 구분)를 수행해 증거를 남긴다. 구현자 확인을 최종 현장 사용성 승인으로 바꾸지 않는다. 간결 요약의 1~2분 읽기는 목표이며 실제 사람 검증 전 달성으로 표시하지 않는다.

- **FR-001**: 시스템은 제공 CSV 5개를 읽고 원본을 변경하지 않아야 한다.
- **FR-002**: 각 사용 기록의 출처와 원본 값·식별자·revision을 추적할 수 있어야 한다.
- **FR-003**: 교대 T는 KST 08:00/20:00이고 기본값은 현재의 가장 최근 교대이며 과거 교대 선택을 제공해야 한다.
- **FR-004**: 알람 received_at, LOT updated_at, 메모 created_at ≤ T로 먼저 가용성을 제한해야 한다.
- **FR-005**: 전체 가용 이력으로 오래된 미해결·진행·보류를 복원하고 최근 24시간은 `(T-24시간,T]`로 계산해야 한다.
- **FR-006**: 같은 입력·T·확정 규칙의 결과가 행 순서에 의해 바뀌면 안 된다.
- **FR-007**: 같은 event_id의 완전 중복은 한 번 반영하고 내용 충돌은 확인 대상으로 보존해야 한다.
- **FR-008**: alarm_instance_id로 사건을 구분하고 설비/코드만으로 다른 사건을 합치면 안 된다.
- **FR-009**: 유효 RAISED 이후 유효 CLEARED가 없는 사건만 확정 미해결로, 해제된 사건은 긴급 미해결에서 제외해야 한다.
- **FR-010**: HEARTBEAT는 전환·발생 건수에 쓰지 않고 공란만으로 상태 불명 알람을 생성하면 안 된다.
- **FR-011**: 고아 해제·동일 시각 전환·상태 ID 누락·충돌은 정상/해결로 확정하지 않고 별도 목록에 둬야 한다.
- **FR-012**: 미해결은 HIGH→MEDIUM→LOW, 같은 심각도는 지속시간 내림차순으로 표시해야 한다.
- **FR-013**: 확인 가능한 발생 시각과 T로 지속시간을 산출하고 불확실한 시간을 임의 생성하면 안 된다.
- **FR-014**: 최근 24시간 같은 설비/코드의 별개 발생 2회 이상을 횟수·마지막 시각으로 표시하되 위험 등급을 올리면 안 된다.
- **FR-015**: 연결/보류 LOT 배지를 제공하되 실제 생산 피해·설비 위험 점수를 확정하면 안 된다.
- **FR-016**: LOT는 당시 가용 최고 revision을 선택하고 동일 버전 상충 원본 중 하나를 임의 선택하면 안 된다.
- **FR-017**: IN_PROGRESS 및 hold_qty > 0 LOT를 각각 진행/보류 사유로 인계해야 한다.
- **FR-018**: 별도 사유 없는 COMPLETE는 제외하고 CANCELLED를 일괄 긴급 취급하면 안 된다.
- **FR-019**: 수량 공란/NULL과 0을 구분해야 한다. 취소 LOT에 편입 조건을 만족하는 승인 메모가 있으면 메모 기반 인계와 후속 업무 존재를 확정하고 보류 수량 미확인·보류 수량 관련 후속 확인 필요성 미확정·조치 완료 미확정을 독립 표시해야 한다. LOT 전체의 후속 확인 여부를 미확정으로 바꾸거나 메모만으로 긴급 확정하면 안 된다.
- **FR-020**: 양품의 투입 초과를 데이터 확인 대상으로 표시하고 원본 보정·과거 버전 대체를 금지해야 한다.
- **FR-021**: 합계 등식 불일치만으로 오류를 확정하거나 검증 안 된 수량의 정상 합계 KPI를 제공하면 안 된다.
- **FR-022**: 독립 인계 사유와 데이터 오류가 함께 있으면 업무를 숨기지 않고 둘을 연결해야 한다.
- **FR-023**: 최근 메모를 기본 표시하고 오래된 관련 메모는 근거 조회로 제공하며 완료 여부를 임의 확정하면 안 된다.
- **FR-024**: 실제 입력의 승인된 12종 문구와 별도로 명시 승인된 예시 문구를 후속 확인·지속 관찰·참고 정보·분류 확인 필요로 명시 분류하고, 다음 조 확인 사항·분류 근거·조치 완료 미확정을 각각 제공해야 한다. 단순 키워드로 분류하지 않고 미등록/모호 문구는 분류 확인 필요로 둬야 한다.
- **FR-025**: 최근 24시간의 승인된 후속 확인 또는 지속 관찰 메모가 LOT에 직접 연결되고 설비 일치가 확인될 때 메모 기반 신규 인계 사유로 사용해야 한다. 참고 정보·분류 확인 필요 메모만으로 LOT를 신규 편입하면 안 된다. 나중에 보류 수량이 0으로 확인돼도 유효한 메모의 후속 업무가 남아 있으면 그 사유로 인계를 유지해야 한다.
- **FR-026**: 메모/LOT 설비가 다르면 원본과 관계 확인을 표시하고 관계 확인 전 그 메모만으로 LOT를 편입하면 안 된다.
- **FR-027**: 오래된 관련 메모 조회를 새 LOT 편입으로 순환시키거나 같은 설비 메모를 특정 알람의 인과 증거로 만들면 안 된다.
- **FR-028**: 우선 알람·이어받을 업무·상태/데이터 확인을 구분하고 대상과 확인 사유 건수를 혼용하면 안 된다.
- **FR-029**: 각 항목에 인계 사유·현재 확인 내용·당시 원본을 제공해야 한다.
- **FR-030**: 선택 T의 요약을 텍스트 복사하고 성공/실패를 알리며 원문도 제공해야 한다.
- **FR-031**: 화면/요약에 제공 기록 기준과 `제공 이력 이전 상태는 확인 불가`를 명시해야 한다.
- **FR-032**: 빈 결과·가용 기록 없음·입력 오류를 구분하고 공장 전체 정상이나 실제 전체 건수로 보장하면 안 된다.
- **FR-033**: 입력 오류 시 읽을 수 있는 부분을 제공하되 불완전 결과임과 누락/오류 범위를 화면·상세·요약에 보존해야 한다. 읽지 못한 범위를 0건/정상으로 나타내면 안 된다.
- **FR-034**: 교대 변경 시 목록·상세·관계·요약이 같은 T를 사용하며 미래 값이 유출되면 안 된다.
- **FR-035**: 실제 데이터와 별도 경계/충돌 사례를 검증하고 실행법·판정 기준·검증 결과·한계를 남겨야 한다.

### Key Entities

- 교대 조회: T, KST, 가용 범위, 입력 완전성, 이력 한계.
- 원본 기록: 파일/위치, 원본 필드, 업무 식별자, 확인 가능 시각.
- 알람 사건: instance, 설비/코드, 가용 이벤트, 상태·심각도·지속시간·재발.
- LOT 상태: lot_id, 가용 revision 후보, 상태/수량/설비, 인계 대상 여부·후속 업무 존재·보류 수량·보류 관련 확인 필요성·조치 완료·긴급도, 인계 사유와 품질 문제. 각 판단은 독립 상태다.
- 메모: note_id, 작성 시각, 설비/LOT 참조, 원문, 승인된 4분류와 근거, 다음 조 확인 사항, 완료 미확정·관계 확인 상태.
- 인계 항목: 대상 유형/ID, 사유, 확인할 내용, 원본 근거, 관련 품질 문제.
- 확인 항목: 불확실/충돌/누락/관계 문제와 관련 대상, 원본 근거.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 담당자가 첫 5분 안에 우선 알람·이어받을 업무·각 항목의 근거라는 세 질문에 답할 수 있다. 실제 사용자 확인 전 달성으로 표시하지 않는다.
- **SC-002**: 모든 인계/확인 항목에서 표시 사유와 원본 근거를 조회할 수 있다(근거 누락 0건).
- **SC-003**: 수용 시나리오에서 미래 기록의 과거 반영, 중복 집계, HEARTBEAT 상태 전환, 불확실한 기록의 정상 확정이 0건이다.
- **SC-004**: 실제 데이터 대조와 별도 충돌/경계 검증이 기대 결과와 일치하고 각 검증의 수행/미수행 상태가 기록된다.
- **SC-005**: 복사 요약에 T·업무/데이터 구분·원본 ID·이력 한계·불완전 여부가 누락되지 않는다.

## Assumptions

- LOT updated_at과 메모 created_at을 가용 시각으로 사용하는 것은 확정된 업무상 가정이며 실제 수신 보장은 아니다.
- 제공 자료는 합성 데이터이고 이력 이전 상태 스냅샷은 제공되지 않는다.
- 원본에 조치 완료·관계 승인 필드가 없어 이를 추정/등록하는 기능은 범위 밖이다.
- 구현 목표 2시간은 확정 판정과 필수 검증을 생략할 권한이 아니다.
- 기술 스택·성능 수치·동시 사용자 수를 임의 확정하지 않는다. 로컬 사용과 제공 데이터 규모가 현재 범위다.
- 메모 12종의 분류는 승인됐다. 분류 확인 필요도 확정된 처리 상태이며 조치 필요/완료의 확정이 아니다. 새 문구 의미는 기본값으로 추측하지 않는다.

## Scope Boundaries

포함: CSV 기반 로컬 브라우저, 현재/과거 교대, 판정/정렬, 업무와 데이터 확인 구분, 원본 상세, 요약 복사, 검증·실행 문서.
제외: DB·로그인·다중 사용자·실시간·제어·예측·위험 점수·외부 AI 문장 해석·조치/관계 승인 등록·원본 보정·합계 대시보드·문서 다운로드.
